# LV01：USB CDC 视频帧协议 v0.1

状态：**设计稿，尚未在电脑端和 STM32 固件中实现或实测**。适用硬件为 STM32F407VET6 核心板与 240×240 ST7789 屏幕。不兼容修改需提高 `version` 并同步更新两端实现和测试向量。

## 1. 链路与职责

```text
MP4/摄像头 → 电脑解码/裁切或缩放 → RGB332 → LV01 封包
            → USB CDC 虚拟串口 → STM32 收帧/校验/转 RGB565
            → SPI3 → ST7789 屏幕
```

电脑负责解码并按视频时间选取画面；STM32 不解析 MP4。CDC 是二进制**字节流**，USB 包、串口库一次 `read` 或 `CDC_Receive_FS` 回调的边界均不代表 LV01 包边界。两个方向的 LV01 流中不得混入调试文本。操作系统串口界面中的波特率设置不决定 USB CDC 链路速率。首版同一时刻最多有一个尚未应答的电脑请求。

## 2. 包格式

所有多字节整数均为**小端序**。所有请求和应答均为 24 字节包头，之后紧跟 `payload_len` 字节载荷；不添加换行、结束符或填充。

| 偏移 | 字节数 | 字段 | v0.1 规则 |
| ---: | ---: | --- | --- |
| 0 | 4 | `magic` | ASCII `LV01`，即 `4C 56 30 31` |
| 4 | 1 | `version` | 固定 `01` |
| 5 | 1 | `type` | 见下表 |
| 6 | 2 | `flags` | 固定 `0000` |
| 8 | 4 | `seq` | 请求序号；应答回显 |
| 12 | 4 | `payload_len` | 载荷字节数 |
| 16 | 4 | `payload_crc32` | 仅对载荷计算；空载荷为 0 |
| 20 | 4 | `header_crc32` | 仅对包头字节 `0..19` 计算 |
| 24 | `payload_len` | `payload` | 紧跟包头 |

CRC-32 使用 IEEE 反射算法：多项式 `0xEDB88320`，初值 `0xFFFFFFFF`，结果异或 `0xFFFFFFFF`；等于 Python `zlib.crc32(data) & 0xffffffff`。CRC 数值写入字段时也按小端序。空载荷的 CRC 为 `0x00000000`。

| `type` | 方向 | 名称 | 载荷字节数 |
| ---: | --- | --- | ---: |
| `01` | 电脑 → 板 | `START` | 8 |
| `02` | 电脑 → 板 | `FRAME` | 57,600 |
| `80` | 板 → 电脑 | `ACK` | 0 |
| `81` | 板 → 电脑 | `NACK` | 4 |

包头 CRC 正确但版本、类型或 `flags` 不支持时回复错误码 5；长度与类型不符时回复错误码 4，不能按错误长度继续接收。magic 或包头 CRC 错误时，不能信任长度/序号，不回复，逐字节重新寻找 `LV01`。

## 3. START 与 FRAME

电脑打开 COM 口后先发送 `START(seq=0)`。其载荷固定为：

| 载荷偏移 | 类型 | 值 |
| ---: | --- | --- |
| 0 | `uint16` | 宽度 240，即 `F0 00` |
| 2 | `uint16` | 高度 240，即 `F0 00` |
| 4 | `uint16` | 目标帧率 8，即 `08 00` |
| 6 | `uint16` | 保留，必须为 0 |

首版仅接受这组参数和 `seq=0`，否则回复 `NACK` 错误码 1。板收到有效 START 后清除上一会话的帧状态，下一帧期望序号置为 1，回复 `ACK(seq=0)`。目标帧率由电脑用于取帧节奏，MCU 不按该字段定时刷新。

电脑收到 `ACK(seq=0)` 后发送 `FRAME(seq=1)`，后续成功帧序号逐次加 1。每个 FRAME 载荷固定为 57,600 字节，即 240×240 个 RGB332 像素。发送完整包后，电脑必须等同序号 ACK 才发送下一帧。板收到完整帧并验证 CRC 后写屏，**整帧写入 LCD 后**才回复 ACK；仅收到 USB 数据不算完成。写屏过程中没有帧缓冲切换，可能有可见撕裂。

载荷 CRC 错误时板不显示，回复错误码 2，仍等待同一序号。电脑最多用相同序号、相同载荷重发两次；再次失败则重新 START。若板已成功显示某序号但 ACK 丢失，再收到该序号的重复帧，板只重发 ACK、不重复显示。其他非期望序号回复错误码 3。新的 START 令序号从 1 重新开始。

## 4. 应答、超时及恢复

ACK 载荷为空，`payload_len=0`、`payload_crc32=0`，`seq` 回显已完成的请求。NACK 载荷是 4 字节小端 `uint32` 错误码，其载荷 CRC 应正常计算，`seq` 回显失败请求。

| 错误码 | 名称 | 电脑端处理 |
| ---: | --- | --- |
| 1 | `BAD_START`：参数或 START 序号错误 | 检查配置，停止发送 |
| 2 | `BAD_PAYLOAD_CRC`：载荷校验失败 | 按上述次数重发同一帧 |
| 3 | `BAD_SEQ`：帧序号错误 | 重新 START |
| 4 | `BAD_LEN`：载荷长度与类型不符 | 检查封包程序，重新 START |
| 5 | `UNSUPPORTED`：版本、类型或 flags 不支持 | 检查两端版本，停止发送 |

接收半包后，**相邻输入字节间隔**超过 300 ms 时丢弃半包并重新搜索包头；这不是整帧总传输时限。START 仅在接收器空闲、等待包头时有效。电脑写完整包后等待 ACK/NACK 最多 1 s；超时则重新 START，从序号 1 发送当前最新画面，忽略旧 ACK。USB 断开/重连后也重新 START。电脑写入需循环直到所有字节实际写完，读取需累积到完整应答。收到校验失败、序号不匹配或未知类型的应答，不据此推进帧序号。

## 5. 像素编码与屏幕写入

载荷按行优先排列，左上角为首像素：`payload[y * 240 + x]` 对应 `(x,y)`，`0 ≤ x,y < 240`。单字节布局为 `RRRGGGBB`。RGB888 量化公式：

```c
uint8_t rgb332 = (r & 0xE0) | ((g >> 3) & 0x1C) | (b >> 6);
```

典型值：黑 `00`、红 `E0`、绿 `1C`、蓝 `03`、白 `FF`。MCU 转 RGB565 的公式：

```c
uint8_t r3 = pixel >> 5;
uint8_t g3 = (pixel >> 2) & 7;
uint8_t b2 = pixel & 3;
uint16_t r5 = (r3 << 2) | (r3 >> 1);
uint16_t g6 = (g3 << 3) | g3;
uint16_t b5 = (b2 << 3) | (b2 << 1) | (b2 >> 1);
uint16_t rgb565 = (r5 << 11) | (g6 << 5) | b5;
```

建议先缓存完整 RGB332 帧并通过 CRC，以免损坏数据被部分显示。每 16 行转换 3,840 个像素到 7,680 字节 RGB565 条带；对 `y=0,16,...,224` 调用 `LCD_SetAddress(0,y,239,y+15)` 和 `LCD_WriteBuff(stripe,3840)`。屏幕驱动将 RGB565 数值以 16 位 SPI 数据格式发送，先发送高位；这与 USB 包头整数的小端序是不同层次。USB 帧载荷为 57,600 字节，LCD 像素传输为 115,200 字节。

## 6. 节奏与测试向量

电脑以 8 fps 为目标，每 125 ms 选取源视频时间轴上的最新画面。若上一帧仍等 ACK，丢弃过期源帧，不积压待发送帧。8 fps 所需 USB 原始像素载荷约 460,800 字节/秒，LCD 原始像素写入约 921,600 字节/秒；未计协议/USB 开销和软件耗时，**不是已验证吞吐率**。

测试向量 A：`START(240,240,8)` 的完整 32 字节包，后 8 字节为载荷：

```text
4C 56 30 31 01 01 00 00 00 00 00 00 08 00 00 00
D5 FA 6F 4A 2A 6F FF FE F0 00 F0 00 08 00 00 00
```

测试向量 B：第一帧全黑，载荷为 **57,600 个 `00`**。其 24 字节包头如下，`00 E1 00 00` 是长度 57,600，`68 F8 A6 3B` 是载荷 CRC：

```text
4C 56 30 31 01 02 00 00 01 00 00 00 00 E1 00 00
68 F8 A6 3B AE 90 B3 D3
```

验收顺序：A → `ACK(seq=0)`；B → 全黑显示 → `ACK(seq=1)`；再用红、绿、蓝、白和彩条核对颜色/方向，最后用运动画面测实际帧率与延迟。
